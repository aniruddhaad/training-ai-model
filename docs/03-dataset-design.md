# FinMod — Dataset Design v0.1

## Status

**Version:** 0.1  
**Status:** Design  
**Project:** FinMod

---

# 1. Objective

Create a small, high-quality, reproducible training corpus for adapting Qwen3-0.6B toward finance and accounting.

The first dataset should prioritize:

1. Quality
2. Diversity
3. Verifiability
4. Clear provenance
5. Controlled experimentation

We will not optimize for the largest possible number of examples.

---

# 2. Dataset Architecture

Dataset v0.1 will contain four major training components:

    Finance-Dataset-v0.1
    |
    +-- Financial reasoning
    |     +-- FinQA
    |     +-- TAT-QA
    |
    +-- Accounting knowledge
    |     +-- NCERT Accounting 11
    |     +-- NCERT Accounting 12
    |
    +-- Verified numerical reasoning
          +-- Synthetic accounting

The components will be processed independently before being combined.

---

# 3. FinQA

## Role

Primary financial numerical reasoning component.

## Source

Official IBM Research FinQA.

## Approximate size

~8,000 QA pairs across ~2,800 financial reports.

## Important fields

Retain, where available:

- id
- pre_text
- post_text
- table
- question
- answer
- final_result
- program_re
- gold_inds

## Why

FinQA teaches the model to reason over financial reports rather than simply memorize finance definitions.

## Processing

We will initially preserve:

- Financial context
- Relevant table
- Question
- Supporting evidence
- Answer
- Reasoning program

We will investigate two possible representations:

### Standard

Context + Question -> Answer

### Reasoning-aware

Context + Question -> Reasoning -> Answer

This allows a future controlled experiment on reasoning supervision.

---

# 4. TAT-QA

## Role

Financial table + text reasoning.

## Why

TAT-QA complements FinQA by emphasizing hybrid reasoning over tables and narrative text.

## Processing

Retain:

- Context
- Table
- Question
- Answer
- Relevant evidence
- Any available reasoning/operation information

The exact source schema and license will be recorded before inclusion.

---

# 5. NCERT Accounting Class 11

## Role

Accounting foundation.

## Approximate size

~4,408 examples.

## Useful fields

- Topic
- Explanation
- Question
- Answer
- Difficulty
- StudentLevel
- QuestionType
- QuestionComplexity
- Prerequisites
- EstimatedTime
- subject
- grade

## Content

Expected focus:

- Accounting fundamentals
- Accounting process
- Double-entry bookkeeping
- Financial statements
- Accounting principles
- Transactions
- Working capital
- Basic accounting concepts

## Processing

Convert each usable example into a standardized instruction/answer format.

Metadata should be retained separately so we can later analyze:

- Difficulty
- Topic
- Student level
- Question type

---

# 6. NCERT Accounting Class 12

## Role

Advanced accounting knowledge.

## Approximate size

~5,730 examples.

## Content

Expected focus:

- Partnership accounting
- Goodwill
- Reconstitution
- Profit-sharing ratios
- Admission/retirement
- Numerical accounting problems
- Application-oriented questions

## Processing

Same standardized format as Class 11.

Retain metadata for later curriculum/difficulty experiments.

---

# 7. Synthetic Accounting Data

## Role

Verified numerical and accounting reasoning.

This dataset will be generated by us.

## Why

External datasets may contain ambiguous or difficult-to-verify answers.

Synthetic examples allow exact validation.

## Initial categories

- Revenue
- COGS
- Gross profit
- Operating expenses
- EBITDA
- EBIT
- PBT
- PAT
- Margins
- ROE
- Debt/equity
- Working capital
- Current ratio
- Quick ratio
- Depreciation
- Interest
- Tax
- Journal entries
- Accruals
- Reconciliation

## Requirement

Every generated example must have a deterministic ground-truth answer.

The generation program must be able to independently recalculate the expected answer.

---

# 8. Unified Training Format

All sources will eventually be converted into a common representation.

Initial conceptual format:

    {
      "messages": [
        {
          "role": "user",
          "content": "..."
        },
        {
          "role": "assistant",
          "content": "..."
        }
      ],
      "metadata": {
        "source": "...",
        "topic": "...",
        "difficulty": "..."
      }
    }

Metadata is not necessarily shown to the model.

It exists for dataset analysis and experiment tracking.

# 9. Data Quality Pipeline

Every dataset will pass through:

    Raw
      |
      v
    Schema inspection
      |
      v
    Normalization
      |
      v
    Duplicate detection
      |
      v
    Quality checks
      |
      v
    Transformation
      |
      v
    Train / validation
      |
      v
    Final dataset

Checks include:

- Missing fields
- Empty questions
- Empty answers
- Duplicate examples
- Near duplicates
- Invalid numerical answers
- Broken formatting
- Excessive prompt boilerplate
- Unexpected language
- Suspicious examples
- Extremely long examples
- Repeated explanations

---

# 10. Dataset Leakage Prevention

Evaluation datasets must never be intentionally included in training.

Evaluation sources:

- FinQA test
- TAT-QA test
- Professional Accounting MMLU
- FinanceBench
- APEX-Accounting
- Our own evaluation benchmark

We must also check for obvious duplicate/near-duplicate examples across training and evaluation datasets.

---

# 11. Initial Dataset Mix

Exact proportions are NOT frozen yet.

Initial hypothesis:

    FinQA/TAT-QA
        ~40-50%

    NCERT Accounting 11/12
        ~30-40%

    Synthetic accounting
        ~10-20%

These percentages are starting hypotheses, not final decisions.

We will inspect actual data distributions before freezing the mix.

---

# 12. Why Not Use All Available Data?

More data is not automatically better.

Potential problems:

- Duplicates
- Repetitive questions
- Conflicting answers
- Different accounting conventions
- Different task formats
- Prompt artifacts
- Low-quality synthetic data
- Licensing/provenance uncertainty

A smaller curated dataset makes the first experiments easier to understand.

---

# 13. Dataset Versions

Dataset versions will be immutable once used in an experiment.

Example:

    Finance-Dataset-v0.1

If preprocessing changes:

    Finance-Dataset-v0.2

If composition changes significantly:

    Finance-Dataset-v1.0

An experiment must always record the exact dataset version.

---

# 14. Experiment Relationship

Example:

    E000
    Qwen3-0.6B
    No fine-tuning
    Baseline

    E001
    Qwen3-0.6B
    Finance-Dataset-v0.1
    LoRA

    E002
    Qwen3-0.6B
    Finance-Dataset-v0.2
    LoRA

This prevents us from losing track of what caused an improvement or regression.

---

# 15. Licensing and Provenance

For every source, record:

- Dataset URL
- Dataset author/organization
- Dataset license
- Underlying content provenance
- Allowed usage
- Known restrictions
- Date inspected

Repository-level license and underlying-content rights must not automatically be assumed to be identical.

This is particularly important for datasets derived from educational or third-party source material.
